## 1. 先明确问题，不急着写代码

已有服务台可以创建、查询工单，也可以更新状态，但看不出谁正在负责处理。
交接时，只改变状态并不能表达责任转移；申请人也不等于处理人。
因此需求首先描述业务问题：**让责任归属清晰可见，让交接有明确结果。**

这时还不能直接决定数据库字段和界面。至少有四个问题需要确认：

| 问题 | 最终决定 | 为什么需要人作决定 |
|---|---|---|
| 每张工单都必须有负责人吗？ | 可以未分配，也可以清空；不推定历史工单的负责人 | 必填与否会改变建单和存量数据处理方式 |
| 负责人从哪里来？ | 固定名单：Alex Chen、Sam Rivera | 对接身份系统和管理名单会显著扩大范围 |
| 只是展示，还是需要筛选？ | 提供全部、两位负责人、未分配四种筛选项 | 这决定功能能否帮助查找个人待办和未分配工作 |
| 在哪里交接，是否受状态限制？ | 仅在详情页操作，四种状态均可；建单不变 | 这决定操作入口，以及是否引入额外业务限制 |

AI 可以发现歧义、提出选项、说明影响，但这些产品取舍需要明确确认。
例如第四项决定同时限制了范围：本次不增加列表内直接分配，也不在建单页增加负责人。

![详情页交接规则的确认](assets/ownership/product-decision.png)

**讲解重点：**先让问题和决定留下记录，再据此修改规格。不要把 AI 自行补全的假设，
事后当成人已经确认的需求。

## 2. Spec 和 Plan 解决不同的问题

### Spec：什么行为才算做对

四轮产品决定逐步形成 Spec v5。规格不仅写“增加负责人”，还规定：

- 负责人和申请人分开显示。
- 已有工单保留原有内容和时间戳，新增的负责人为空，不重置或重新灌入数据。
- 分配、转交、清空负责人时，不能顺带改变状态。
- 保存状态时，不能顺带提交尚未保存的负责人选择。
- 筛选条件同时生效；选择“全部负责人”只取消负责人条件。
- 非法负责人、工单不存在、保存失败，都不能显示成成功。

这些约束可以被测试和实际操作验证，因而比“界面要好用”“不要影响原功能”更有用。
[Spec v5 的具体版本](https://github.com/huangyingting/ai-native-sdlc-demo/blob/9e183465d985bfa081f239a68eda400340320195/docs/delivery-runs/brownfield-human-gated-delivery/1/spec.md)
获得批准后，才成为后续工作依据。

![Spec v5 批准及处理回执](assets/ownership/spec-approved.png)

### Plan：怎样实施，怎样证明

[Plan v1](https://github.com/huangyingting/ai-native-sdlc-demo/blob/6b7a4ddf96f43c6f1980c2e1ed4b568ec429d427/docs/delivery-runs/brownfield-human-gated-delivery/1/plan.md)
把验收场景映射到六项实施任务，覆盖模型与迁移、数据读写、服务端操作、
详情页、列表筛选和验证。任务有依赖关系，也说明受影响的文件与检查方式。

Spec 回答“结果应当是什么”，Plan 回答“怎样在现有系统里实现，并证明它没有破坏约束”。
批准 Spec 不等于批准 Plan；批准 Plan 也不等于批准代码。

![Plan v1 的独立批准](assets/ownership/plan-approved.png)

## 3. 先审查测试，而不是只追求绿灯

[测试 PR](https://github.com/huangyingting/ai-native-sdlc-demo/pull/8)
只能修改测试和预期失败清单，不能提前实现功能。
这里使用的是**受控 Red**：已有测试通过，新增测试因为功能缺失而失败，
失败名称还必须和已记录的清单精确一致。

### 第一轮：失败原因必须可信

首次检查发现，清单中的测试名称带有 ` > `，与 Vitest JSON 报告中的完整名称不一致。
审查还发现所谓“历史数据库”是通过当前数据层创建的，未来加上新字段后，
它便不再代表真正的旧表结构；部分筛选与交接测试也没有验证实际行为。

确认问题后提交修改要求，让 Coding Agent 补齐，而不是放宽验证器。

### 第二轮：CI 通过，测试本身仍可能有错

修订后的受控 Red 已经通过，但进一步审查发现：

- 同时筛选 `open` 和 `VPN`，却期望得到一张 `in_progress` 工单。
- 真正修改负责人之后，仍要求保留原来的更新时间。
- 测试把页面渲染在未挂入文档的容器中，却通过整个文档查找元素。
- 检查重复保存时没有推进时间，无法识别错误的时间戳重写。

为什么 CI 没有发现？因为这些错误断言位于更早的预期失败之后，尚未执行到。
**精确匹配 Red 只能证明失败符合约定，不能证明后面的所有断言都合理。**

![第二轮要求修改：指出被预期失败遮住的问题](assets/ownership/tests-request-changes.png)

### 最终测试基线

修正后，再次检查确切提交 `104be08`：

| 检查 | 结果 |
|---|---|
| 原有基线测试 | 26 项通过 |
| 测试 PR 的全部测试 | 38 项：29 项通过，9 项预期断言失败 |
| 跳过、基础设施或未处理错误 | 0 |
| lint、类型检查、生产构建 | 通过 |

![最终受控 Red 检查通过](assets/ownership/tests-controlled-red.png)

随后才[批准测试](https://github.com/huangyingting/ai-native-sdlc-demo/pull/8#pullrequestreview-5486995544)，
合并到交付分支并启动实现。批准后的测试、规格、计划和审核记录冻结，
不能在实现阶段通过削弱测试来获得 Green。

## 4. 实现阶段：让同一份约定从 Red 变成 Green

[实现 PR](https://github.com/huangyingting/ai-native-sdlc-demo/pull/9)
增加了可空负责人字段、固定名单、SQLite 增量迁移、详情页操作和列表筛选。
它复用已有下拉控件，没有引入身份系统，也没有修改建单流程。

最终检查中，**38 项测试全部通过，包括之前的 9 项 Red**；
9 个冻结的文档和测试文件保持不变。实现阶段的重点不是测试数量变多，
而是同一组已审查的要求通过产品代码得到满足。

![Implementation Green 检查](assets/ownership/implementation-green.png)

代码审查之外，还运行了确切版本，检查实际页面：

- 未点击保存或应用前，选择不会自动生效。
- 状态和负责人两个表单独立保存。
- 转交后刷新页面仍显示正确负责人。
- 重复保存相同负责人，整条记录和更新时间均不变。
- 列表仍按优先级和创建时间排序，概览数字不随筛选改变。
- 键盘选择、取消、焦点恢复及窄屏布局可用；非法负责人得到明确错误提示。

本地容器构建曾遇到依赖下载的 TLS 握手错误，因此实现审查使用了同一提交的
原生生产构建和未修改的锁文件。没有关闭 TLS 校验，也没有把这一步称为镜像验收。

确认后，[实现批准](https://github.com/huangyingting/ai-native-sdlc-demo/pull/9#pullrequestreview-5487362172)
绑定到 `4ee8225`，正常合并为 `1a1e14d`。两者文件树完全一致。

![实现的独立批准](assets/ownership/implementation-approved.png)

## 5. 代码合并以后，交付仍可能失败

发布流程先构建镜像，再上传 GHCR，然后按不可变摘要启动镜像验证。
实际发布时，构建成功，但上传失败：

```text
denied: permission_denied: write_package
```

![镜像包权限阻止发布，验证任务没有执行](assets/ownership/publication-blocked.png)

任务日志已经显示 `Packages: write`，但这不等于现有镜像包已授权给当前仓库。
操作者检查并配置包的 **Manage Actions access**，给当前仓库 **Write** 权限后，
第三次执行成功。这里需要的是权限修正，不是修改业务代码，更不是删除失败记录。

![权限修复后，发布与镜像验证通过](assets/ownership/publication-passed.png)

这也说明，人机协作不限于“审批代码”：遇到外部资源授权时，AI 应说明失败证据和
所需操作，让有权限的人处理，而不是擅自扩大授权。

## 6. 验证交付物，不用源码预览代替

最终镜像为：

```text
ghcr.io/huangyingting/ai-native-sdlc-demo-it-service-desk@sha256:90836abf909410db91b0d3c791812683e5424c5cab7d7a84df1af6772a66ce76
```

云端验证确认镜像能启动、健康接口和列表可访问、初始四条数据正确。
这仍只是基线检查，因此又拉取上述确切摘要，在隔离数据卷和本机回环地址上运行，
验证负责人功能，而不是沿用前面源码预览的结论。

### 看交接结果，而不只看操作按钮

以下页面来自**已经发布的镜像**。申请人仍是 Maya Chen，负责人是 Sam Rivera。
四种工单状态下分别执行分配、转交和清空，共 12 个组合，刷新后逐项检查结果。

### 看筛选是否共同生效

## 7. 最后由人验收确切版本

发布成功没有自动关闭需求。流程先给出镜像摘要和验证结果，再等待明确验收。
确认后提交：

```text
/sdlc accept sha256:90836abf909410db91b0d3c791812683e5424c5cab7d7a84df1af6772a66ce76
```

验收意见同时说明依据和范围。系统记录命令回执后，才关闭需求。
本案例中的浏览器核验由 AI 助手执行；产品决策、阶段批准和最终验收由用户逐项确认，
不能把自动化检查描述成人亲自执行过的操作。

![确切镜像验收、命令回执和需求关闭](assets/ownership/accepted.png)

## 8. 这条流程值得复用的是什么

| 阶段 | 人负责什么 | AI 和自动化负责什么 | 进入下一步的依据 |
|---|---|---|---|
| 需求澄清 | 确认目标和产品取舍 | 发现歧义、提出选项、修订规格 | 明确记录的决定 |
| Spec、Plan | 审查具体版本 | 生成文档、建立任务与验收映射 | 版本绑定的批准 |
| Tests | 判断测试是否表达了正确要求 | 编写测试、验证精确 Red、按意见修正 | 合理且可执行的测试基线 |
| Implementation | 审查实现及验证证据 | 修改代码、运行 Green、核验页面 | 同一测试约定通过且冻结文件未变 |
| Delivery | 处理必要授权，判断是否验收 | 发布、按摘要运行、记录结果 | 确切交付物的验证和验收 |

AI-native 的价值不是取消这些责任，而是让 AI 在明确边界内持续推进，
把人的时间集中在真正需要判断的地方。失败同样是证据：测试逻辑有误、权限不足、
本地构建受阻，都应被识别、解释和处理，而不是被一个绿灯掩盖。

**未包含的结论：**本案例不证明生产可用性、容量、SLA 或安全风险已解决。
[基线准备记录](preparation.md)中的 8 项依赖告警仍未处理；本次运行是临时本地部署，
不是持续对外提供服务的网站。数据库就绪检查、发布可靠性和后续工程案例另行开展。
