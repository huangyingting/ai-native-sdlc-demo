## 核心机制深度拆解

为了透彻理解本交付主线的方法论设计，下文系统拆解该特性的**核心痛点、人机协作拓扑、全生命周期阶段门禁与质量保证机制**。

### 1. 核心痛点与工程挑战

在为存量遗留系统添加看似简单的新功能（如“工单责任人指派”）时，技术团队常遭遇以下典型挑战：

- **业务规则模糊与责任人混淆**：需求提出时往往只描述“加个下拉框”，未厘清“工单申请人”与“当前负责人”的区别、未界定存量历史工单如何处理，以及未明确指派与工单状态机是否存在耦合。
- **AI 随意发挥导致范围失控**：大模型在直接接手任务时，容易盲目引入未经评审的外部账号系统、过度重构建单流程，甚至擅自修改无关模块代码。
- **形式主义红绿灯测试**：测试虽然看似全绿，但断言薄弱（仅断言 HTML 标签存在），无法甄别底层是否发生数据重复写入或更新时间戳误篡改。

### 2. 人机分工与协作拓扑

本交付严格遵循“人类把关决策、AI 负责提案与实现、流水线自动归档”的分工模型：

```text

  │                             │ ──触发──> │ 2. 起草 Spec 规格说明草案   │
  │ 3. 逐项审查问答，拍板 4 项决策│ <──提问── │    (挖掘规则歧义提出选择)    │
  │ 4. 批准 Spec v5 与 Plan v1  │           │                             │
  │                             │ ──触发──> │ 5. 编写测试套件 (TDD Tests) │
  │ 6. 审查测试用例，断言受控 Red │ <──提交── │    (受控红灯，严禁偷跑代码) │
  │                             │ ──交接──> │ 7. 编写功能实现 (Implementation)
```

### 3. 全生命周期五重门禁机制

1. **规格说明门禁 (Spec Gate)**：历经 4 轮严谨问答确立 4 项产品决策，消除所有业务盲区后批准并冻结 Spec v5。
2. **实施计划门禁 (Plan Gate)**：将验收场景系统化拆解为 6 项具体工程任务，核验文件改动边界后批准并冻结 Plan v1。
3. **受控测试门禁 (Tests Gate)**：测试套件先行，严格验证 26 项老测试全绿、9 项新测试精准 Red 失败，杜绝基础设施报错。
4. **功能实现门禁 (Implementation Gate)**：由 Coding Agent 独立编码兑现契约，实现 38 项测试 100% 绿灯全过，已冻结契约文件逐字节未变。
5. **不可变镜像验收门禁 (Image Acceptance Gate)**：基于构建的生产镜像 Digest 拉起临时沙箱，由人工在隔离实例上核验 12 项流转组合与 7 项筛选逻辑后签署正式验收。

### 4. 三重质量保证机制

1. **不可变契约与防篡改冻结机制**：在进入开发阶段前，Spec 与 Plan 经过哈希绑定并严格冻结；实现阶段严禁通过削弱断言来换取测试转绿。
2. **底层数据版本与时间戳硬断言**：借助 SQLite 的 `PRAGMA data_version`，物理级核验重复保存相同负责人时不产生底层写入，严禁依靠肉眼主观判断。
3. **确切镜像交付物现场核验**：坚决不用本地热更新代码糊弄验收，所有验收截图与操作均直接基于拉取的正式发布 Docker 镜像展开。

## 1. 深入澄清业务痛点，杜绝盲目编码

在既有系统中，IT 服务台已支持创建、查询与更新工单状态，但始终无法标识究竟由谁在跟进处理。在工单流转交接时，单纯变更工单状态无法体现责任主体的转移，且工单“申请人”绝不等同于“处理人”。因此，本次需求从根本的业务痛点出发：**使工单责任归属清晰透明，使流转交接具有明确的确定性。**

在需求初始阶段，切勿急于敲定数据库字段或前端 UI。至少有 4 个核心架构与产品问题亟待决策澄清：

| 核心问题 | 最终业务决策 | 为什么必须由人类做决策 |
|---|---|---|
| 每张工单是否必须指定负责人？ | 允许为空（未分配），支持清空负责人；严禁为历史存量工单推断或填充假定负责人。 | 必填与否直接颠覆工单创建链路与历史存量数据的兼容迁移逻辑。 |
| 候选负责人名单由何处提供？ | 采用内置的固定成员名单：Alex Chen 与 Sam Rivera。 | 若对接外部 LDAP/SSO 或新增成员管理模块，将导致交付范围不可控地膨胀。 |
| 仅需在页面展示，还是需要支持检索筛选？ | 支持“全部”、“Alex Chen”、“Sam Rivera”、“未分配” 4 类选项的组合筛选。 | 这直接决定了该功能能否切实解决一线工程师查找个人待办与未分配工单的痛点。 |
| 在何处触发交接？是否受工单当前状态制约？ | 仅在工单详情页支持交接，且在全部 4 种状态下均可操作；新建工单流程不变。 | 决定了交互入口以及是否引入额外的业务状态机限制。 |

在这一阶段，AI 的核心价值在于精准发掘业务规则中的模糊地带、给出备选方案并分析技术影响；但最终的权衡取舍必须由人类架构师和业务负责人明确拍板。例如，上述第 4 项决策明确收窄了本期范围：暂不开发工单列表页直接分配功能，亦不在创建工单入口增加负责人字段。

![详情页交接规则的确认](assets/ownership/product-decision.png)

**核心原则**：务必让每一个业务问题与对应决策在 Issue 中留痕归档，进而据此迭代规格说明（Spec）。切勿将 AI 擅自臆测的默认行为，在事后包装成所谓“已确认的业务需求”。

## 2. 规格（Spec）与实施计划（Plan）承载不同的工程职责

### 规格说明（Spec）：界定“什么才算做对”

历经 4 轮严谨的产品问答，规格说明演进至 Spec v5。该版本不仅写明“增加负责人字段”，更严格规范了以下业务不变量：

- 页面布局必须清晰区分展示工单“申请人”与“负责人”。
- 数据库升级时，存量工单完整保留原业务内容与历史更新时间戳，新增的负责人字段填充为空（NULL），严禁重置或篡改历史数据。
- 指派、转交或清空负责人时，不得附带改变工单的状态。
- 点击“保存状态”按钮时，绝不能同时提交尚未保存的负责人变更（两表单完全解耦）。
- 筛选条件支持按 AND 取交集生效；选中“全部负责人”时仅清除负责人维度的筛选条件。
- 面对非法负责人参数、工单不存在或数据库写入异常，系统绝不能给出虚假的成功提示。

这些硬性约束均具备高度的可测试性与可验证性，远比模糊的“界面要美观易用”、“不要影响老功能”更具工程约束力。只有当 [Spec v5 的具体修订版本](https://github.com/huangyingting/ai-native-sdlc-demo/blob/9e183465d985bfa081f239a68eda400340320195/docs/delivery-runs/brownfield-human-gated-delivery/1/spec.md)
获得人类正式批准后，它才具备作为后续实施基准的权威性。

![Spec v5 批准及处理回执](assets/ownership/spec-approved.png)

### 实施计划（Plan）：明确“如何安全落地并提供证明”

在通过的 [Plan v1](https://github.com/huangyingting/ai-native-sdlc-demo/blob/6b7a4ddf96f43c6f1980c2e1ed4b568ec429d427/docs/delivery-runs/brownfield-human-gated-delivery/1/plan.md) 中，
所有验收场景被系统化拆解为 6 项具体的工程任务：涵盖数据模型与迁移脚本、数据持久层读写、Server Actions 服务端操作、详情页 UI、列表多维筛选及独立验证。计划中清晰指明了各项任务之间的依赖关系、影响的文件边界以及验证手段。

Spec 负责定义“系统的预期行为是什么”，Plan 负责界定“如何在现有复杂工程中落地实现，并证明未破坏任何既有约束”。因此，批准 Spec 不等于批准 Plan，批准 Plan 也绝不能免去后续对功能代码的严格审查。

![Plan v1 的独立批准](assets/ownership/plan-approved.png)

## 3. 测试套件先行审查，而非片面追求绿灯

[测试套件 PR](https://github.com/huangyingting/ai-native-sdlc-demo/pull/8)
被严格限制为仅允许提交测试用例与预期失败清单（expected failures），严禁在测试分支中偷跑实现代码。
此处采用的是严格的**受控红灯（Controlled Red）机制**：既有的所有回归测试必须保持全部通过，而新增的业务用例因待测功能尚未实现而预期失败，且失败的测试用例名称与报错范围必须与清单精准一致。

### 第一轮审查：测试失败原因必须真实可信

在首次 CI 校验中发现，清单中登记的测试用例名带有 ` > ` 路径，与 Vitest JSON 报告导出的完整层级名称不匹配导致校验中断。进一步审查发现，测试代码中所谓的“历史数据样本”竟然是通过当前修改后的数据层在内存中动态生成的——这意味着未来一旦加上新字段，它就无法再模拟真实的旧表结构；此外，部分筛选与交接测试并未对底层数据库执行真实断言。

审查者当即提交了修改要求（Request Changes），由 Coding Agent 重新补充真实数据迁移样本，绝不通过放宽校验器规则来掩盖问题。

### 第二轮审查：CI 门禁通过，测试逻辑仍可能存在暗坑

修订后的测试套件虽然在受控 Red 门禁中被判定通过，但审查者深入检视代码时敏锐发现：

- 测试用例在同时指定 `open` 状态与 `VPN` 关键词筛选时，断言预期居然期望返回一张 `in_progress` 的工单（逻辑自相矛盾）。
- 在测试成功变更负责人的场景中，断言竟然依然要求保留原始的 `updated_at` 时间戳不变。
- 前端测试在未将组件挂载进真实 DOM 树的临时容器中渲染，却在断言中通过全局 `document` 查找元素，造成隐式越界污染。
- 在验证“重复保存相同负责人不产生副作用”时，测试未推进模拟时钟，根本无法检测出底层是否错误触发了时间戳刷新。

为什么自动化 CI 没能拦截这些错误断言？因为这些用例在更早的前置断言处就已经因功能未实现而抛出了预期失败，后续的逻辑错误根本尚未被执行到。**自动化门禁能够证明测试失败符合清单约定，但无法证明后续断言在逻辑上全部严谨。人类审查者的工程判断力不可替代。**

![第二轮要求修改：指出被预期失败遮住的问题](assets/ownership/tests-request-changes.png)

### 冻结的最终测试基线

经多轮修正后，审查者基于确切提交 `104be08` 执行最终复核：

| 校验维度 | 实际检查结果 |
|---|---|
| 原有基线回归测试 | 全部 26 项用例绿灯通过 |
| 测试 PR 包含的完整测试集 | 全部 38 项：29 项通过，9 项为精确匹配的业务预期失败（Red） |
| 跳过用例（skip）、环境故障或未捕获异常 | 0 |
| ESLint、TypeScript 类型检查、生产构建 | 全部通过 |

![最终受控 Red 检查通过](assets/ownership/tests-controlled-red.png)

在所有测试用例经过严密推敲后，审查者正式[批准测试 PR](https://github.com/huangyingting/ai-native-sdlc-demo/pull/8#pullrequestreview-5486995544)，将其合并至交付生命周期分支并正式下发实现任务。获批的测试用例、规格说明与计划即刻冻结，在后续编码阶段，严禁通过删改或削弱断言来换取测试转绿。

## 4. 编码实现阶段：让已冻结的约定从 Red 变为 Green

由 Coding Agent 提交的[功能实现 PR](https://github.com/huangyingting/ai-native-sdlc-demo/pull/9)

在最终流水线检查中，**全部 38 项测试用例实现 100% 绿灯转绿，之前处于受控 Red 的 9 项业务断言全部通过**；9 个已冻结的文档与测试文件未发生任何篡改。实现阶段的核心衡量标准，绝非测试数量的盲目增加，而是原有已获批的需求与断言被业务代码严谨、完整地兑现。

![Implementation Green 检查](assets/ownership/implementation-green.png)

在代码审查之余，审查者运行该版本，针对真实前端页面进行了深入校验：

- 在用户尚未点击“保存”或“应用筛选”按钮前，表单选择绝不自动生效或触发网络请求。
- 工单“状态变更”与“负责人变更”作为两个独立的 Form 表单，提交互不干扰。
- 成功交接负责人后，强刷浏览器页面，负责人数据依然准确持久化展示。

- 工单列表仍严格按优先级与创建时间降序排列，顶部的各状态统计徽标不因局部筛选而发生错误变动。
- 键盘 Tab 切换选择、Esc 取消、焦点自动恢复以及移动端窄屏自适应均正常工作；提交非法参数时能够弹出明确的友好提示。

## 5. 代码合并完成，不等于交付万事大吉

在现代工程交付中，合并代码仅是前置步骤。持续交付流水线必须先自动构建镜像、推送到容器镜像仓库（GHCR），随后基于不可变的镜像内容摘要（Digest）拉起临时验证容器。
在首次正式发布运行时，虽然 Docker 构建步骤顺利通过，但在推送至 GHCR 时被直接拦截报错：

```text
denied: permission_denied: write_package
```

![镜像包权限阻止发布，验证任务没有执行](assets/ownership/publication-blocked.png)

虽然工作流日志表面上声明了 `Packages: write`，但这并不意味着 GitHub Packages 现存的包资源已向当前仓库授予了写入权限。操作者迅速介入排查，在镜像包设置的 **Manage Actions access** 中显式为当前仓库授予了 **Write** 权限后，第 3 次流水线重试即刻顺利发布。这充分证明：人机协同不仅限于“审查代码”；当遇到外部云基础设施鉴权受阻时，AI 应当清晰呈现失败上下文并指导排查路径，由具备特权的人类运维人员安全处置，而非擅自越权。

![权限修复后，发布与镜像验证通过](assets/ownership/publication-passed.png)

## 6. 严肃验证确切交付物，绝不用本地热更新源码糊弄验收

本次流水线最终构建并推送的不可变生产镜像为：


## 7. 终审把关：由人类明确签署最终交付验收

流水线构建发布成功，绝不自动关闭业务需求。工作流在主 Issue 中发布包含镜像精确摘要与冒烟测试通过记录的验收提示，耐心等待业务负责人的终审裁决。在全面核验无误后，负责人正式提交验收命令：

```text
/sdlc accept sha256:90836abf909410db91b0d3c791812683e5424c5cab7d7a84df1af6772a66ce76
```

验收评论中清晰载明了本次验收的核对依据与检验边界。自动化工作流校验指令签名合法并记录审计回执后，该业务需求 Issue 才宣告正式关闭。在本案例中，浏览器端操作核验由 AI 助手辅助执行，而业务决策、阶段性门禁批准与最终镜像验收均由人类工程师逐项把关，绝不将脚本自动化检查混淆为人类的亲自主观验收。

## 8. 值得全行业复用的 AI 原生交付模式

| 交付阶段 | 人类的核心职责 | AI 与自动化的核心职责 | 晋级至下一阶段的准入凭据 |
|---|---|---|---|
| **需求澄清 (Intent)** | 确立业务核心目标与边界取舍 | 挖掘规则歧义、提供备选方案、起草规格说明 | 在 Issue 中显式留痕的决策评论 |
| **规格与计划 (Spec/Plan)** | 逐阶段审查并批准文档版本 | 自动生成文档、建立实施任务与验收场景的严密映射 | 绑定精确版本哈希的审批指令 |
| **测试套件 (Tests)** | 审视测试用例是否真实反映了规格约束 | 编写测试断言、提供精确受控 Red 状态、响应评审修改 | 包含受控 Red 断言的冻结测试套件 |
| **功能实现 (Implementation)** | 审查代码 Diff、架构合理性与安全边界 | 自主编写功能代码、使全量测试转绿、配合界面核验 | 测试全绿且已冻结文件 Hash 保持未变 |
| **生产交付 (Delivery)** | 处理特权资源鉴权，进行现场业务验收 | 自动构建发布、基于镜像摘要拉起验证、留存审计线索 | 基于确切不可变交付物的验收签署 |

AI-native 的价值不是取消这些责任，而是让 AI 在明确边界内持续推进，
把人的时间集中在真正需要判断的地方。失败同样是证据：测试逻辑有误、权限不足、
本地构建受阻，都应被识别、解释和处理，而不是被一个绿灯掩盖。
