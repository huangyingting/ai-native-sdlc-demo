## 演练结论与客观边界

在两次完全独立执行、分别使用全新测试数据卷的演练中，系统均 100% 通过验证。
两次演练均严格遵循既定策略：首先精准拦截存在配置异常的候选实例，平稳放行健康候选实例；在检测到人工暂停注入的故障后，精确触发且仅触发 1 次回滚切换至稳定实例。两次演练均完整保留了候选实例上产生的受控数据库写入记录。

需要明确的是：本次记录属于**运行时故障恢复验证凭据**，不代表发起了新的生产发布、不代表已批准代码级修复，亦不构成生产级 SLO 承诺或已闭环的预防性维护计划。

## 端到端实测演练时序

```text
部署稳定实例并挂载全新测试数据卷
    → 准入拦截：拒绝未挂载卷的错误配置实例
    → 准入放行：启动健康候选实例，验证网关路由成功切流
    → 受控写入：向候选实例写入测试工单数据
    → 故障注入：在第 3 次健康采样前人工暂停候选容器进程
    → 连续 2 次采样失败 → 精准触发 1 次自动回滚
    → 流量切回稳定实例持续健康 → 告警事件平稳恢复
    → 解除暂停 → 进入独立恢复观察窗口
    → 再次拒绝错误配置实例 → 自动清理测试资源
```

稳定实例与健康的候选实例运行**同一个不可变 Docker 镜像**，每次演练均在专属的全新测试数据卷上独立开展。配置错误的故障实例特意配置了无效数据库路径且不挂载任何数据卷。网关仅在本地回环地址（localhost）暴露只读流量；受控写入使用资格规范中约定的 Alex Chen / Sam Rivera 成员名单。

网关层返回的真实响应能够确凿证明流量提升与自动回退，坚决不以候选实例单点自测健康作为依据。在注入暂停故障前，脚本明确校验受控业务写入已落盘。两次演练中，写入完成后的整行数据与表结构 Hash 均与回退完成后的 Hash 完全一致，且与初始空库 Hash 明确不同，证明故障与回滚未造成任何数据丢失。

| 连续监测采样总次数 | 10 | 10 |
| 健康采样数 / 失败采样数 | 8 / 2 | 8 / 2 |

两次演练拥有各自独立的事件 ID、审计凭证与数据卷。第二次演练属于严肃的独立复现实验，绝非隐藏失败后的重试，亦不覆盖首次演练的数据。采样周期**并不等同于系统真实对外停机时长**，上述指标亦不作为生产环境下的 MTTR 或 SLA 承诺。探测超时时间会直接影响观测到的故障检测周期。

## 运维维护审查要点

本次演练的故障根因完全已知：系测试人员主动暂停候选容器所致。
演练证明了现有的准入机制足够严密，在两次演练的恢复前后均稳定拒绝了错误配置。

系统自动生成的维护分析草案**目前尚未获得人工正式批准**。草案中自动生成的“原因未明”或“建议增加未实现的检查项”等模板化描述，不能直接作为本次受控实验的正式复盘结论。在启动后续开发前，团队必须组织正式审查，厘清已知注入点、现有规则防御能力、责任主体与后续改进事项。服务自动恢复本身不会自动批准维护规格，亦不代表免除预防性维护的责任。

## 尚未覆盖的边界说明

- 本实验未覆盖跨大版本灰度发布、数据库 Schema 破坏性变更回滚或多机房集群流量调度。
- 本地单并发网关与受控写入无法替代高并发写竞争场景下的完整安全性测试。
- 有限窗口的采样观测无法作为系统长期高可用性或 SQLite 并发锁超时的权威认证。
- 历史基线中存在的 8 项依赖告警依然保留；功能性验收不等于生产级合规审计。
- 演练结束后，所有测试容器、测试数据卷与本地网关均已销毁清理；截图中的本地端口不代表在线服务。

## 现场演示与复现建议

建议在演示时按顺序呈现：首先展示准入策略对异常实例的精准拦截，接着展示网关平稳提升健康候选实例，随后呈现连续 2 次采样失败后触发的 1 次平滑回退，最后核验写入数据 Hash 的完整一致性。最后明确指出维护审查的严肃边界，切勿声称系统已实现“完全无人值守的主动自愈”。
