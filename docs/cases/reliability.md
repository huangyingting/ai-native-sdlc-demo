# 发布可靠性：准入拦截、故障感知与自动回滚演练

[English](reliability.en.md) · [案例索引](README.md) · [就绪检查前置条件](readiness.md)

**工程附录声明**：本次演练基于确定性的自动化控制脚本运行，属于工程能力验证实验，而非由 AI 自主决断触发系统恢复。演练全程未发起任何额外的 Copilot CLI 诊断或自动修复调用。
固定的演练脚本严格针对此前已交付的生产镜像，执行资格前置核验、故障主动注入、实时健康监测与自动回退。（详见[演示目标与 Copilot 角色规范](../copilot-roles.md)）。

## 核心机制深度拆解

为了透彻理解本演练的工程价值，下文系统拆解该可靠性闭环的**设计背景、系统拓扑、执行时序与质量保证机制**。

### 1. 业务背景与经典工程痛点

在现代软件发布中，团队往往误以为“容器拉起、进程存活”就代表发布成功，但在复杂生产环境中常遭遇以下致命陷阱：

- **假存活（False Liveness）陷阱**：新容器虽然成功启动（进程存活检查 `GET /api/health` 正常返回 200），但底层数据库连接串或路径配置错误，导致真实的业务接口全量抛出 500。若流量无脑切入，将直接导致业务雪崩。
- **运行时无响应与缺乏回滚保护**：新版本刚接入流量，可能因锁竞争或外部依赖卡死而陷入假死状态。若缺乏高灵敏度的自动化感知与秒级回退，将造成长时间业务中断。
- **回滚过程中的数据丢失风险**：如果系统触发回滚切回旧版本，故障发生前一线用户在新版本上已经提交写入的数据是否会被静默篡改、覆盖或丢失？
- **“自愈即结项”的管理误区**：系统自动回滚成功后，容易被误当成“故障已解决”，导致坏配置被反复推上线，埋下长效隐患。

本演练的目标正是用一套**确定性的自动化控制闭环**，逐一破解上述痛点。

### 2. 系统拓扑与三方角色设计

演练在本地通过 Docker 调度构建了一套微型高可用发布沙箱：

```text
               外部请求流量
                    │
                    ▼
          ┌───────────────────┐
          │  本地网关 (Gateway) │ (负责切流、健康监测、阈值判定与触发回滚)
          └─────────┬─────────┘
                    │
      ┌─────────────┼─────────────┐
      ▼             ▼             ▼
┌───────────┐ ┌───────────┐ ┌───────────────┐
│ 稳定老实例  │ │ 候选新实例  │ │ 错误配置故障实例│
│  (stable) │ │(candidate)│ │  (bad-config) │
└─────┬─────┘ └─────┬─────┘ └───────┬───────┘
      │             │               │
      └──────┬──────┘               ▼
             ▼                 (无挂载数据卷)
    [共享测试 SQLite 数据卷]      (数据库路径指向 /dev/null)
```

- **本地调度网关 (Gateway)**：充当智能反向代理。它对外暴露服务入口，对内维护活动发布（Active Release）指针，支持 `promote()`（提升新版本为主力）与 `rollback()`（自动回退至上一稳定版本）。
- **三类 Docker 容器实例（均基于同一不可变生产镜像）**：
  - **`stable`（稳定老实例）**：基准运行实例，挂载全新生成的测试数据卷，保持健康可用。
  - **`candidate`（候选新实例）**：准备上线接流的目标实例，挂载同一个测试数据卷。
  - **`bad-config`（配置错误实例）**：特意将数据库路径配置为无效的 `/dev/null`，且不挂载任何数据卷，用于模拟配置失误的候选版本。
- **共享持久化存储**：真实的 SQLite 数据卷，承载工单数据。

### 3. 四阶段时序运行机制

```text
阶段一：准入拦截
  网关尝试切换流量至 bad-config → 探测就绪接口返回 503 → 准入拒绝，稳定实例继续承载流量

阶段二：平稳切流与受控写入
  启动候选实例 candidate → 探测就绪通过 → 网关切流成功 → 候选实例受控写入数据并计算数据快照 Hash B

阶段三：主动故障注入与阈值回滚
  执行 docker pause 挂起 candidate 进程 → 网关连续 2 次探测失败触发告警 → 自动切流回滚至 stable
  → 重新计算数据库 Hash C，严格断言 Hash C === Hash B（数据零丢失）

阶段四：故障自愈、防复发与运维复盘
  执行 docker unpause 恢复 candidate → 经过连续健康窗口复核自愈 → 再次尝试准入 bad-config 确认依然被拒
  → 自动生成结构化运维复盘工单 maintenance-intent.md
```

- **阶段一（准入拦截）**：网关在尝试将流量切换到 `bad-config` 时，主动发起就绪探测。由于该实例数据库不可读，`GET /api/ready` 抛出 503，网关直接拒绝切流，流量保持在老版本，证明坏配置绝无法上线。
- **阶段二（切流与受控写入）**：网关验证 `candidate` 正常就绪后将流量切入。在故障发生前，对数据库全部表结构与数据行生成 SHA-256 快照，并在候选实例上执行真实的工单负责人写入（生成新的数据快照 Hash B）。
- **阶段三（故障感知与自动回退）**：通过 Docker 底层 API 执行 `docker pause` 故意挂起候选容器。网关每 200ms 发起一次探测，连续检测到 2 次超时/失败（达到故障判定阈值）时，立即自动触发 `gateway.rollback()`，流量平滑切回 `stable` 实例。回滚后立即比对数据库哈希 Hash C，严格验证数据未遭破坏。
- **阶段四（自愈、防复发与复盘）**：对候选实例解除暂停，并在独立的观察窗口内验证其连续健康状态；再次尝试推上错误配置，确认防御规则依然严格生效；最终自动导出结构化运维工单，交由人类工程师复盘。

### 4. 三重质量保证机制

为了杜绝演练沦为“纸上谈兵”，框架确立了三项严密的工程保证：

1. **存活探针与就绪探针物理隔离（Liveness vs Readiness）**：
   存活探测（`GET /api/health`）仅用于确认 Node.js 进程没有挂；而就绪探测（`GET /api/ready`）强制对真实的工单表发起 `SELECT id FROM tickets LIMIT 1` 只读查询。哪怕进程存活，只要数据库断连，就绪检查必定返回 503，彻底消除“假存活”风险。
2. **底层数据库全量 SHA-256 结构快照比对**：
   不只是简单对比“工单条数是不是 4 条”，而是将 SQLite 的底层表结构元数据（`PRAGMA table_info`）与全量数据行按 ID 排序序列化后计算 SHA-256。只要表结构发生损坏或字段遭到意外篡改，快照比对便会直接报错中断。
3. **变异测试前置准入（Mutation Testing Qualification）**：
   在正式执行发布演练前，必须先行运行前置资格核验：测试框架会在源码中主动注入 6 种恶意的逻辑变异（如漏读数据库、掩盖报错、篡改缓存头等）。只有证实测试套件能够**100% 精准捕杀全部 6 处代码变异**，才允许放行进入发布演练，防止出现“测试虽然全绿，但实际查不出任何缺陷”的形式主义用例。

## 演练结论与客观边界

在两次完全独立执行、分别使用全新测试数据卷的演练中，系统均 100% 通过验证。
两次演练均严格遵循既定策略：首先精准拦截存在配置异常的候选实例，平稳放行健康候选实例；在检测到人工暂停注入的故障后，精确触发且仅触发 1 次回滚切换至稳定实例。两次演练均完整保留了候选实例上产生的受控数据库写入记录。

## 端到端实测演练时序

```text
部署稳定实例并挂载全新测试数据卷
    → 准入拦截：拒绝未挂载卷的错误配置实例
    → 准入放行：启动健康候选实例，验证网关路由成功切流
    → 受控写入：向候选实例写入测试工单数据
    → 故障注入：在第 3 次健康采样前人工暂停候选容器进程
    → 连续 2 次采样失败 → 精准触发 1 次自动回滚
    → 流量切回稳定实例持续健康 → 告警事件平稳恢复
    → 解除暂停 → 进入独立恢复观察窗口
    → 再次拒绝错误配置实例 → 自动清理测试资源
```

稳定实例与健康的候选实例运行**同一个不可变 Docker 镜像**，每次演练均在专属的全新测试数据卷上独立开展。配置错误的故障实例特意配置了无效数据库路径且不挂载任何数据卷。网关仅在本地回环地址（localhost）暴露只读流量；受控写入使用资格规范中约定的 Alex Chen / Sam Rivera 成员名单。

网关层返回的真实响应能够确凿证明流量提升与自动回退，坚决不以候选实例单点自测健康作为依据。在注入暂停故障前，脚本明确校验受控业务写入已落盘。两次演练中，写入完成后的整行数据与表结构 Hash 均与回退完成后的 Hash 完全一致，且与初始空库 Hash 明确不同，证明故障与回滚未造成任何数据丢失。

## 运维维护审查要点

本次演练的故障根因完全已知：系测试人员主动暂停候选容器所致。
演练证明了现有的准入机制足够严密，在两次演练的恢复前后均稳定拒绝了错误配置。

系统自动生成的维护分析草案**目前尚未获得人工正式批准**。草案中自动生成的“原因未明”或“建议增加未实现的检查项”等模板化描述，不能直接作为本次受控实验的正式复盘结论。在启动后续开发前，团队必须组织正式审查，厘清已知注入点、现有规则防御能力、责任主体与后续改进事项。服务自动恢复本身不会自动批准维护规格，亦不代表免除预防性维护的责任。

## 尚未覆盖的边界说明

- 本实验未覆盖跨大版本灰度发布、数据库 Schema 破坏性变更回滚或多机房集群流量调度。
- 本地单并发网关与受控写入无法替代高并发写竞争场景下的完整安全性测试。
- 有限窗口的采样观测无法作为系统长期高可用性或 SQLite 并发锁超时的权威认证。
- 历史基线中存在的 8 项依赖告警依然保留；功能性验收不等于生产级合规审计。
- 演练结束后，所有测试容器、测试数据卷与本地网关均已销毁清理；截图中的本地端口不代表在线服务。
